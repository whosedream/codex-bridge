# Direct Codex Workers

In Antigravity Orchestrator mode, delegate code implementation and development tests to Codex by default, even when the user only describes the work. The planner defines the scope and the acceptance suite. The executor calls the bridge directly from the same conversation. The host owns final acceptance.

1. **Test-first implementation.** Call `codex_run` with `model: "gpt-6.2-sol"`, `async_mode: true`, and `sandbox: "workspace-write"`. Tell the worker to write a focused regression test first, run it against the unchanged implementation, and verify that it fails for the intended reason. Tell the same worker to make the smallest implementation change, run the same test again, and run relevant existing tests. Ask for the actual commands, red and green outcomes, and the paths changed by this task. If the red case cannot be reproduced, report it explicitly. Use `codex_poll` to retrieve the implementation result.
2. **Independent read-only review.** After implementation completes, call `codex_review` as a separate read-only Codex session. Use `mode: "uncommitted"` with a focus prompt identifying the task and exact worker diff or changed paths, including new test files. If the changed-file list was truncated, use the complete list at `details_path`. Do not resume the implementation session or use `invoke_subagent`. Exclude pre-existing local changes. For a file already dirty before the task, give the reviewer the task's own before/after patch so it can distinguish those changes. Request concrete findings with locations, or a clear statement that there are no findings. Poll any running review and wait for its result before reporting completion.
3. **Host acceptance.** In Antigravity, independently run the agreed acceptance suite once on the final code. Include authorized checks that need the host, such as socket, GPU, or network tests that are unavailable in the worker sandbox. If the full suite covers the focused tests, run the full suite alone. Rerun relevant checks only to diagnose a failure or after code changes. Route fixes through the implementation worker and review the updated diff in a fresh read-only session. Report worker tests, host acceptance, and independent review findings separately, including failures and checks that remain unverified.

Use this workflow for ordinary code changes. Honor explicit workflow or model overrides from the user.

Keep read-only exploration and planning in Antigravity unless the user asks to delegate them.

When the user delegates a task to Codex, the Antigravity primary agent calls the Codex Bridge MCP tools from the current conversation. Call `codex_run` directly for execution. Keep the user's requested model, scope, constraints, and verification in the brief. When no model is requested, omit `model` to use the Codex configuration.

- In a WSL installation with both endpoints, use `codex-bridge_codex-wsl` for Linux absolute paths such as `/home/…`; send Windows drive-letter and UNC paths to `codex-bridge_codex`. Use the same endpoint for readiness, dispatch, follow-up, and polling.
- Use an absolute `cwd` for the workspace the user authorized. Use `workspace-write` for approved edits and `read-only` for inspection or non-editing execution.
- Dispatch background work once with `codex_run(async_mode=true)`. Keep the returned `task_id` and wait for a completion notification if the client provides one for that task. Otherwise use `codex_poll(task_id)` for the 300-second default or `wait_seconds=600` for longer tasks. Explicit shorter waits and `wait_seconds=0` remain available. After `running`, keep waiting on that ID. Report completion, failure, or a decision the user needs to make.
- Call `codex_plan` directly if the user wants a read-only proposal. Call `codex_review` directly for code review. Pass the same workspace and the prior `session_id` to `codex_run` to continue a Codex conversation.
- Keep parallel writes in separate worktrees or run them sequentially. Codex Bridge runs in the supplied directory.
- Use the compact receipt for changed files, the short diff stat, verification evidence, and failures or unverified checks. The receipt gives counts for pre-existing dirty files. If `changed_files_truncated` is true or you need exact attribution or logs, read the local file at `details_path`. Report the result in the user's language.
